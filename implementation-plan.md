# План реализации Magic Pet

## Цель плана

Проект собирается короткими walkthrough-инкрементами. После каждого walkthrough приложение остаётся запускаемым, а добавленное поведение можно проверить отдельно.

Ключевое решение: уже после walkthrough 1 доступен весь основной пользовательский путь — от `/start` до второго уровня питомца. В первом срезе используются память, локальные планы и текстовый резерв вместо ещё не подключённых инфраструктурных деталей. Следующие walkthrough не переписывают сценарий заново, а заменяют реализации за стабильными интерфейсами.

Этот порядок намеренно отличается от послойной реализации из технической спецификации: он нужен, чтобы начать пользовательское тестирование как можно раньше.

## Правила выполнения

- Один walkthrough — один законченный, проверяемый инкремент.
- Следующий walkthrough начинается только после зелёных тестов и ручного smoke-прохода текущего.
- Временные реализации создаются за интерфейсами: `UserStore`, `PlanGenerator`, `AssetCatalog`, `TelegramGateway`. Поэтому память, fallback и заглушки можно заменить без изменения пользовательского сценария.
- Каждый walkthrough завершается обновлением короткой инструкции запуска и списка известных ограничений.
- Бинарные ассеты в эти walkthrough не генерируются: пользователь добавляет их отдельно по согласованным путям.
- Секреты никогда не попадают в Git, тестовые фикстуры, логи или JSON с контентом.
- Версии библиотек фиксируются при выполнении walkthrough 1 после проверки совместимости с Java 21.

## Контент и промпты с первого walkthrough

В проекте сразу создаются два независимых JSON-ресурса:

```text
src/main/resources/content/ui-texts.ru.json
src/main/resources/prompts/plan-generator.ru.json
```

`ui-texts.ru.json` содержит весь контролируемый приложением пользовательский текст:

- подписи кнопок;
- статичные сообщения и ошибки;
- параметризованные шаблоны сообщений, например прогресс и эволюция;
- текстовые резервы на случай отсутствия изображения или AI.

Динамические значения — имя питомца, цель, названия и описания сгенерированных задач, XP и уровень — формируются доменной логикой и подставляются в шаблоны. Callback ID (`scenario:study`, `action:task_done` и другие) остаются стабильными константами в коде и не зависят от текста кнопки.

Предварительная форма файла текстов:

```json
{
  "buttons": {
    "scenarioStudy": "📚 Учёба",
    "scenarioSport": "🔥 Спорт",
    "scenarioBlog": "🦊 Личный блог",
    "taskDone": "✅ Выполнено"
  },
  "messages": {
    "chooseScenario": "Выбери путь для своего Magic Pet",
    "askPetName": "Как назовём твоего Magic Pet?",
    "askGoal": "Какой цели ты хочешь достичь?",
    "fallbackPlanUsed": "Архив Magic Pet подготовил проверенный маршрут"
  },
  "templates": {
    "progress": "{petName} получает {xpAdded} XP. Всего: {totalXp} XP.",
    "levelUp": "{petName} достиг уровня {level}!"
  }
}
```

`plan-generator.ru.json` содержит только инструкции для генерации плана:

- системную роль;
- общие ограничения;
- отдельные ограничения для `STUDY`, `SPORT` и `BLOG`;
- требование ровно трёх задач;
- контракт структурированного ответа;
- правило безопасности для спорта.

Предварительная форма файла промптов:

```json
{
  "version": 1,
  "system": "Ты составляешь короткий безопасный план для пользователя Magic Pet.",
  "rules": [
    "Верни ровно три задачи",
    "Первые две задачи выполняются за 1–3 минуты",
    "Третья задача является следующим шагом после урока",
    "Не назначай XP и уровень"
  ],
  "scenarioRules": {
    "STUDY": ["Используй простой поддерживающий язык"],
    "SPORT": ["Не давай медицинских, экстремальных или потенциально опасных советов"],
    "BLOG": ["Предлагай конкретные короткие творческие действия"]
  },
  "responseContract": {
    "summary": "string",
    "tasks": [
      {"title": "string", "description": "string"}
    ]
  }
}
```

В API отправляются собранный из этого файла промпт, сценарий и очищенный текст цели. Telegram ID, username и любые токены в промпт не попадают. JSON создаётся в walkthrough 1 и проверяется тестом на структуру, а реально используется AI-клиентом с walkthrough 4.

## Walkthrough 1 — сквозной работающий бот

### Результат

Минимальная, но целая версия продукта работает в Telegram. Можно пройти путь:

1. Запустить Java-приложение с токеном из `.env`.
2. Отправить `/start`.
3. Выбрать любой из трёх сценариев.
4. Ввести имя питомца.
5. Ввести цель.
6. Получить локальный план из трёх задач.
7. Дважды нажать «Выполнено».
8. Получить 100 XP и увидеть переход на уровень 2.

### Что реализуем

- Gradle-проект на Java 21, точка входа и `.env.example`.
- Изолированный адаптер Telegram long polling и нормализованный `IncomingMessage`.
- Стабильные порты `TelegramGateway`, `UserStore`, `PlanGenerator` и `AssetCatalog`.
- `InMemoryUserStore` для состояния одного процесса.
- Полную конечную машину основного onboarding-сценария.
- Три локальных fallback-плана: учёба, спорт, личный блог.
- XP: 50 за задачу; уровни 1 и 2; повторное нажатие не выдаёт XP второй раз.
- Текстовый показ питомца. Если подходящий PNG уже лежит на ожидаемом пути, бот может отправить его; отсутствие файла не мешает сценарию.
- `ui-texts.ru.json` и `plan-generator.ru.json`, загрузку и раннюю валидацию обоих ресурсов.
- Fake Telegram gateway для сквозного автоматического теста без сети.
- Понятную ошибку старта при отсутствии `TELEGRAM_BOT_TOKEN`.

### Пока намеренно не делаем

- сохранение после перезапуска;
- реальный AI-вызов;
- обязательные изображения;
- управление произвольными пользовательскими задачами;
- подготовку отдельного worktree для урока.

### Проверка

- `./gradlew test` проходит.
- Сквозной тест проводит fake-пользователя от `/start` до уровня 2.
- Тест ресурсов подтверждает, что оба JSON валидны и обязательные ключи присутствуют.
- Ручной smoke в Telegram проходит по всем восьми шагам результата.
- Повторное нажатие «Выполнено» не увеличивает XP.

### Точка пользовательского тестирования

После этого walkthrough уже можно оценивать тексты, понятность кнопок, длину сценария, эмоциональность эволюции и то, где пользователь теряется. Ограничение теста: состояние исчезает при остановке приложения, план пока шаблонный, картинка необязательна.

## Walkthrough 2 — SQLite и сохранение состояния

### Результат

Тот же сценарий продолжает работать после перезапуска, а несколько Telegram-пользователей полностью изолированы.

### Что реализуем

- SQLite, JDBC и Flyway.
- Неизменяемую миграцию `V1__initial_schema.sql` для `users`, `pets`, `goals` и `tasks`.
- `SqliteUserStore` вместо in-memory реализации через тот же порт.
- Восстановление текущего состояния, питомца, цели и активной задачи после перезапуска.
- Транзакционное завершение задачи и начисление XP.
- Идемпотентность повторного callback.
- Ограничение: один питомец и одна активная цель на пользователя.

### Проверка

- Все миграции применяются к пустой временной базе.
- Приложение перезапускается посередине onboarding и посередине плана без потери прогресса.
- Два Telegram ID не видят и не меняют данные друг друга.
- Два одинаковых callback дают только одну награду.
- Сквозной тест walkthrough 1 проходит уже с SQLite.

## Walkthrough 3 — полноценные ассеты питомцев

### Результат

Бот показывает правильный PNG для каждой пары `scenario + level` и безопасно работает, пока пользователь добавляет или заменяет ассеты.

### Что реализуем

- `FileAssetCatalog` и строгую карту ожидаемых путей:

```text
assets/study/level-1.png
assets/study/level-2.png
assets/sport/level-1.png
assets/sport/level-2.png
assets/blog/level-1.png
assets/blog/level-2.png
assets/common/fallback.png
```

- Отправку изображения при первом показе питомца и при эволюции.
- Проверку типа, читаемости и наличия файла без декодирования бизнес-логикой.
- Текстовый fallback, если конкретный файл ещё не добавлен.
- Документ `assets/README.md` с требованиями: PNG, 1024×1024, без текста внутри изображения.

### Проверка

- Табличный тест покрывает все шесть сочетаний сценария и уровня.
- Отсутствующий или повреждённый файл не прерывает диалог.
- Ручной smoke подтверждает смену изображения после второй задачи.

## Walkthrough 4 — AI-план и гарантированный fallback

### Результат

Цель пользователя превращается в персональный план через школьный AI-прокси. Любая проблема AI незаметно переключает бота на локальный план, поэтому урок не срывается.

### Что реализуем

- HTTP-клиент к прокси за интерфейсом `PlanGenerator`.
- Сборку промпта из `plan-generator.ru.json`.
- DTO структурированного ответа и строгую валидацию: ровно три задачи, непустые поля, лимиты длины и допустимый сценарий.
- Отдельную проверку безопасного содержания для спорта на уровне доступных детерминированных правил.
- Таймауты и fallback при сетевой ошибке, невалидном JSON, нарушении контракта или небезопасном результате.
- Поле `source = AI | FALLBACK` в сохранённых задачах.
- Нейтральное пользовательское сообщение о резервном маршруте без технических деталей.

### Входное условие

До начала этого walkthrough нужен точный контракт школьного AI-прокси: URL, авторизация, формат запроса и формат ответа. До его получения остальные walkthrough не блокируются.

### Проверка

- Контрактные тесты на успешный ответ, timeout, HTTP-ошибку, сломанный JSON, две/четыре задачи и небезопасный спортивный совет.
- Ни в одном запросе и логе нет Telegram ID, username или токенов.
- При отключённой сети полный путь до уровня 2 остаётся проходимым на fallback-плане.

## Walkthrough 5 — управление задачами

### Результат

Помимо трёх задач первоначального плана пользователь может добавлять и просматривать собственные задачи, открывать детали, выполнять или удалять их. Выполненные задачи не засоряют активный список.

### Что реализуем

- Кнопки «Мои задачи», «Добавить задачу» и «Выполненные».
- Пошаговый ввод короткого названия и описания новой задачи.
- Позицию задачи в очереди и статус `PENDING | COMPLETED`.
- Список только активных задач в виде Telegram-кнопок с короткими названиями.
- Карточку выбранной задачи: описание и действия «Выполнено»/«Удалить».
- Отдельный список выполненных задач.
- Стабильный callback с внутренним ID задачи и обязательной проверкой владельца.
- Явное решение по XP: пользовательская задача награждает теми же 50 XP, если иное не будет зафиксировано до выполнения walkthrough.

### Проверка

- Созданная задача сохраняется после перезапуска.
- Выполненная задача исчезает из активных и появляется во «Выполненных».
- Удалённая задача больше не отображается и не может выдать XP.
- Пользователь не может открыть, удалить или завершить чужую задачу подставленным callback ID.
- Пустые списки и слишком длинные названия обрабатываются понятным сообщением.

## Walkthrough 6 — устойчивость и эксплуатационная безопасность

### Результат

Типовые сбои не ломают урок и не показывают пользователю технические подробности.

### Что реализуем

- Централизованную конфигурацию с проверкой обязательных значений.
- Безопасные логи без токенов, промптов с пользовательскими данными и stack trace в Telegram.
- Обработку неожиданного текста для каждого состояния: повтор текущей подсказки вместо сброса.
- Лимиты длины имени питомца, цели, названия и описания задачи.
- Поведение при недоступном Telegram, занятой/повреждённой SQLite и отсутствующем ассете.
- Ограниченное повторное подключение к Telegram с понятным статусом в IDE.
- Команду безопасного сброса только для режима разработки/урока; она не включается случайно в обычном режиме.

### Проверка

- Набор негативных тестов проходит без повреждения состояния.
- Поиск по логам и исключениям не находит значений секретов.
- После временной AI- или Telegram-ошибки приложение возвращается в рабочее состояние по описанному сценарию.

## Walkthrough 7 — учебная поверхность

### Результат

Сложная инфраструктура скрыта, а студент работает почти исключительно с `lesson/StudentBot.java` и понятным `PetFacade`.

### Что реализуем

- Финальный API `PetFacade` с методами уровня продукта.
- `StudentBot.java` без Telegram SDK, SQL, HTTP, JSON и файловых путей.
- Не более 3–4 одновременно незавершённых учебных участков.
- Три обязательных типа изменения: добавить кнопку, написать `if/else`, вызвать готовый метод.
- Творческое изменение через `ui-texts.ru.json` или явно выделенную безопасную константу — после прогона выбирается более понятный вариант.
- Эталонную завершённую версию для МОПа и стартовую учебную версию.
- Короткие подсказки, которые не раскрывают решение целиком.

### Проверка

- Начальная учебная версия запускается и содержит только запланированные TODO.
- После выполнения TODO студент проходит тот же сквозной тест, что и эталонная версия.
- В `StudentBot.java` отсутствуют импорты TelegramBots, JDBC и HTTP-клиента.
- Внутренний прогон подтверждает, что новичок может объяснить одно условие и один вызов метода.

## Walkthrough 8 — подготовка нового занятия

### Результат

МОП одной командой получает чистый изолированный проект для конкретного лида, не наследующий `.env`, SQLite или прогресс предыдущего занятия.

### Входное условие

Проект должен находиться в Git-репозитории с веткой `main`. На момент составления плана текущий каталог не распознаётся командой `git status` как worktree; это нужно исправить или выполнять walkthrough в исходном Git-репозитории. Первые семь walkthrough это не блокирует.

### Что реализуем

- `prepare-lesson` с безопасной нормализацией имени и фамилии.
- Новую ветку `lesson/<slug>-<date>` от `main` и отдельный Git worktree.
- Чистые `.env` и `data`, без копирования секретов и старой базы.
- Проверки чистоты исходного дерева, существования `main` и конфликта имён.
- Понятный вывод: путь к проекту, что открыть в IntelliJ, какие два значения нужно заполнить.
- Инструкцию ротации/отзыва школьного токена после урока.

### Проверка

- Два последовательных запуска создают независимые окружения.
- Секрет и база первого окружения не появляются во втором.
- Ошибка на любом шаге не оставляет частично подготовленное окружение без явного сообщения.

## Walkthrough 9 — финальная приёмка и пилот

### Результат

Получаем воспроизводимую версию для внутреннего прогона и открытого урока.

### Что реализуем

- Единый smoke-чеклист для всех трёх сценариев.
- Инструкцию запуска, аварийного перехода на fallback и восстановления рабочей версии.
- Автоматизированный набор unit/integration-тестов из технической спецификации.
- Проверку старта из чистого worktree одной кнопкой IntelliJ.
- Замер пути `/start` → ответ бота и полного учебного сценария.
- Фиксацию найденных на пилоте проблем отдельным списком, без расширения scope прямо во время прогона.

### Финальная приёмка

- Все три сценария доходят до уровня 2.
- После перезапуска сохраняются состояние, задачи и XP.
- Два пользователя изолированы.
- AI-ошибка, отсутствующий ассет и повторный callback не срывают урок.
- Пользовательские задачи корректно добавляются, открываются, завершаются и удаляются.
- Учебный файл содержит не больше 3–4 TODO.
- Чистое окружение для следующего лида создаётся воспроизводимо.

## Зависимости между walkthrough

```text
1 Сквозной бот
└── 2 SQLite
    ├── 3 Ассеты
    ├── 4 AI и fallback
    └── 5 Управление задачами
        └── 6 Устойчивость
            └── 7 Учебная поверхность
                └── 8 Подготовка занятия
                    └── 9 Финальная приёмка
```

Walkthrough 3 и 4 после завершения walkthrough 2 технически независимы. При необходимости их можно поменять местами; основной путь останется рабочим.

## Вопросы, которые не блокируют старт

- Точный контракт школьного AI-прокси нужен только к walkthrough 4.
- Финальные PNG нужны только для визуальной приёмки walkthrough 3; до этого работает текстовый fallback.
- Окончательные формулировки кнопок можно менять в `ui-texts.ru.json` без изменения callback и бизнес-логики.
- Политика удаления внутренних веток нужна к walkthrough 8.
- Решение, получают ли добавленные пользователем задачи 50 XP, окончательно фиксируется перед walkthrough 5.
