# Walkthrough 10 — двенадцать студенческих задач

## Цель

Подготовить три равных учебных маршрута. В каждом маршруте студент получает четыре самостоятельных GitHub Issues:

- два понятных пользовательских бага;
- две небольшие функции с видимым результатом в Telegram.

Студент не создаёт инфраструктуру с нуля. Он работает как начинающий разработчик в существующем проекте: читает README, воспроизводит проблему, находит небольшой участок, меняет несколько строк и проверяет результат в настоящем боте.

Этот walkthrough описывает изменения эталонного решения, необходимые для того, чтобы все двенадцать задач были честно выполнимы абсолютным новичком.

## Принятые решения

- Эталонный `main` содержит полностью исправленный и реализованный продукт.
- Для каждого маршрута существует один стартовый patch: `study.patch`, `sport.patch` или `blog.patch`.
- Patch превращает эталонное решение в учебное: добавляет два дефекта, убирает две функции и оставляет четыре понятных `TODO STUDENT`.
- `prepare-lesson` применяет только patch выбранного маршрута в отдельном worktree.
- Остальные два маршрута в этом worktree остаются рабочими примерами для сравнения.
- На уроке МОП выбирает одну или две задачи. Остальные остаются backlog того же маршрута.
- Готовые ответы не находятся в студенческой issue-карточке.

| Sport / Игнис | Функция | Кнопка «Подсказка» | кнопка → готовый метод без изменения XP |

## Целевой пользовательский опыт

Каждая задача должна иметь одинаковую форму:

1. **Что происходит сейчас** — наблюдаемое поведение в Telegram.
2. **Как должно работать** — один конкретный результат.
3. **Как воспроизвести** — 3–6 пользовательских шагов.
4. **С чего начать** — ссылка на конкретный раздел README.
5. **Что сделать** — действия без готового ответа.
6. **Подсказки** — от человеческого наблюдения к нужным 3–5 строкам.
7. **Готово, если** — только наблюдаемые критерии.

В issue нельзя использовать неизвестный термин без объяснения. Фразы вида «открой ветку `case SPORT`» запрещены. Git-ветка, ветка `if` и ветка `switch` — разные понятия; новичку нельзя предлагать угадывать значение слова по контексту.

## Целевая структура учебного кода

Текущий `StudentBot` слишком общий: изменение одного обработчика влияет на все маршруты. Перед созданием двенадцати задач разделить учебную поверхность:

```text
src/main/java/studio/pixelpoint/magicpet/lesson/
  StudentBot.java
  route/
    LessonRoute.java
    LessonRouteRegistry.java
    StudyLesson.java
    SportLesson.java
    BlogLesson.java
```

### StudentBot

Оставить только общий порядок обработки:

- `/start`;
- выбор подходящего `LessonRoute`;
- передача кнопки выбранному маршруту;
- передача текста выбранному маршруту;
- общий fallback `repeatPrompt`.

В `StudentBot` не должно быть деталей Telegram SDK, SQL, HTTP, путей к PNG и реализации конкретных студенческих задач.

### LessonRoute

Интерфейс нужен инфраструктуре, но студенту не требуется его изменять. Минимальный контракт:

```java
interface LessonRoute {
    Scenario scenario();
    boolean selectionPressed(IncomingMessage message);
    void select(PetFacade pet, UserSession user);
    void acceptPetName(PetFacade pet, UserSession user, String name);
    List<Button> taskButtons();
    boolean handleButton(PetFacade pet, UserSession user, IncomingMessage message);
    void afterTaskCompleted(PetFacade pet, UserSession user, ProgressResult result);
}
```

Точные сигнатуры можно адаптировать, но все четыре задачи маршрута должны быть видны в одном небольшом классе. Целевой размер каждого `*Lesson.java` — не больше 120–150 строк.

### Три route-класса

Классы имеют одинаковую структуру и разные данные. Поэтому студент может открыть рабочий соседний маршрут и сравнить решения, не читая весь проект.

В каждом файле добавить четыре явно подписанных блока:

```java
// ISSUE 1 — первый баг
// ISSUE 2 — второй баг
// ISSUE 3 — первая функция
// ISSUE 4 — вторая функция
```

В эталонном `main` под комментариями находится правильный код. Стартовый patch заменяет его на дефект или `TODO STUDENT`.

## Подготовить простой API PetFacade

Студент должен соединять готовые продуктовые действия, а не писать SQLite и Telegram-код. В `PetFacade` подготовить и протестировать методы:

```java
void showPet(UserSession user);
void showPet(UserSession user, int displayedLevel);
void beginPetRename(UserSession user);
void renamePet(UserSession user, String newName);
void showHint(UserSession user);
void showLevelProgress(UserSession user);
void showPlan(UserSession user);
void confirmTaskDeletion(UserSession user, long taskId);
void deleteTask(UserSession user, long taskId);
```

Названия должны читаться как обычные действия. Каждый метод скрывает отправку Telegram-сообщений, работу с SQLite, выбор ассетов и форматирование.

### Завершение текущей задачи

Сейчас `PetFacade.completeCurrentTask(...)` одновременно меняет данные, отправляет сообщения и выбирает изображение. Для бага с устаревшим изображением разделить действие и отображение:

```java
ProgressResult completeCurrentTask(UserSession user, String deliveryId);
UserSession refreshUser(UserSession user);
void showProgress(UserSession user, ProgressResult result);
void showLevelUp(UserSession user, ProgressResult result);
```

После этого конкретный route-класс сможет явно показать Pet нужного уровня. Эталонный Sport-код использует фактический уровень из `ProgressResult`; стартовый patch подставляет `1`.

Если это разделение сильно раздувает учебный файл, допустима одна готовая операция `finishTaskAndReturnResult(...)`, но уровень изображения всё равно должен быть видимым аргументом в `SportLesson`.

## Общие продуктовые изменения

### Переименование Pet

Добавить состояние `WAITING_PET_RENAME` и готовые методы домена:

- `beginPetRename()` — запоминает, куда вернуться, и начинает ожидать текст;
- `renamePet(String)` — проверяет имя, сохраняет его и возвращает пользователя к активному плану;
- сохранение нового имени уже использует существующее поле `pets.name`, новая миграция для имени не нужна.

Если для возврата требуется отдельное поле состояния, добавить его новой Flyway-миграцией, не изменяя уже применённые `V1` и `V2`.

### Подсказки

Подсказка не должна зависеть от AI. Добавить ресурс:

```text
src/main/resources/content/task-hints.ru.json
```

Минимальная структура: три короткие подсказки для каждой пары `scenario + position`. Для пользовательской задачи использовать общий текст: «Раздели задачу на самый маленький первый шаг».

`showHint(user)` определяет текущий сценарий и номер задачи, отправляет одну короткую подсказку и не меняет статус задачи или XP.

### Прогресс до уровня

Добавить в `LevelProgression` безопасный метод уровня продукта:

```java
static int experienceToNextLevel(int experience);
```

Для максимального уровня использовать отдельный результат или `OptionalInt`, чтобы `PetFacade` мог отправить «Достигнут максимальный уровень».

### Полный план

`showPlan(user)` использует уже сохранённые `UserSession.tasks()` и показывает:

- `✅` для выполненных;
- `👉` для текущей;
- `⏳` для будущих.

Метод ничего не меняет и не начисляет XP.

### Подтверждение удаления

Не добавлять новое состояние и таблицу. Передавать ID задачи внутри callback:

```text
task:confirm_delete:<id>
task:delete:<id>
task:open:<id>
```

Первое действие только показывает вопрос. «Да» использует существующее удаление. «Нет» снова открывает карточку задачи.

## Маршрут Study / Руни

Порядок Issues важен: сначала два бага, затем две функции.

### S1. После выбора появляется другой Pet

**Эталонное решение:** `StudyLesson.select(...)` вызывает выбор `Scenario.STUDY`.

**Стартовый patch:** заменяет аргумент на `Scenario.SPORT` и добавляет `TODO STUDENT`.

**Что меняет студент:** одно значение в вызове готового метода.

**Контрактный тест:** после нажатия `scenario:study` пользователь имеет сценарий `STUDY`.

### S2. Бот не запоминает имя

**Эталонное решение:** `StudyLesson.acceptPetName(...)` передаёт в `pet.namePet(...)` текст, введённый пользователем.

**Стартовый patch:** передаёт фиксированное имя `Руни` вместо пользовательского текста.

**Что меняет студент:** заменяет фиксированный текст переменной `name`.

**Контрактный тест:** имя `Искорка` отображается сразу и после восстановления из SQLite.

### S3. Кнопка «Мой Pet»

**Эталонное решение:** `StudyLesson.taskButtons()` содержит кнопку `action:show_pet`, а `handleButton(...)` вызывает `pet.showPet(user)`.

**Стартовый patch:** удаляет кнопку и обработчик, оставляя два соседних `TODO STUDENT`.

**Что меняет студент:** повторяет форму рабочей информационной кнопки и вызывает один готовый метод.

**Контрактный тест:** кнопка отправляет правильный ассет, имя, XP и уровень, не меняя задачу.

### S4. Переименование Pet

**Эталонное решение:** кнопка `action:rename_pet` вызывает `beginPetRename`; следующее текстовое сообщение в состоянии `WAITING_PET_RENAME` вызывает `renamePet`.

**Стартовый patch:** удаляет обе связи, но инфраструктура и методы остаются готовыми.

**Что меняет студент:** добавляет кнопку, один обработчик нажатия и один обработчик текста по образцу первоначального имени.

**Контрактный тест:** новое имя сохраняется после перезапуска, пустое и слишком длинное имя отклоняются.

## Маршрут Sport / Игнис

### I1. На 100 XP нет нового уровня

**Эталонное решение:** `LevelProgression.levelFor(100)` возвращает `2`.

**Стартовый patch:** меняет сравнение `>= 100` на `> 100` и добавляет `TODO STUDENT` рядом с условием.

**Что меняет студент:** один оператор сравнения в указанном README файле.

**Контрактный тест:** отдельные проверки для 99, 100, 249 и 250 XP.

### I2. Изображение осталось старым

**Эталонное решение:** `SportLesson.afterTaskCompleted(...)` при повышении передаёт в показ изображения новый уровень из результата.

**Стартовый patch:** передаёт фиксированный уровень `1`.

**Что меняет студент:** заменяет фиксированное число текущим значением уровня.

**Контрактный тест:** при 100 XP отправляется `assets/sport/level-2.png`, а при 250 — `level-3.png`.

### I3. Кнопка «Подсказка»

**Эталонное решение:** кнопка `action:hint` вызывает `pet.showHint(user)`.

**Стартовый patch:** удаляет кнопку и обработчик. `task-hints.ru.json` и фасад остаются готовыми.

**Что меняет студент:** добавляет кнопку и один вызов метода.

**Контрактный тест:** подсказка соответствует текущему заданию, XP и статус не изменяются.

### I4. Кнопка «До следующего уровня»

**Эталонное решение:** кнопка `action:level_progress` вызывает `pet.showLevelProgress(user)`.

**Стартовый patch:** удаляет кнопку и обработчик.

**Что меняет студент:** добавляет вторую информационную кнопку по образцу подсказки.

**Контрактный тест:** 50 XP → осталось 50; 100 XP → осталось 150; максимальный уровень → специальное сообщение.

## Маршрут Blog / Скриба

### B1. «Мои задачи» показывает выполненные

**Эталонное решение:** обработчик `action:my_tasks` вызывает `showTasks(user, false)`.

**Стартовый patch:** передаёт `true`.

**Что меняет студент:** одно логическое значение после сравнения двух соседних обработчиков.

**Контрактный тест:** активная задача видна только в активных, выполненная — только в выполненных.

### B2. «Удалить» выполняет задачу

**Эталонное решение до B3:** подтверждённое удаление вызывает `deleteTask(user, taskId)`.

**Стартовый patch:** вызывает `completeTask(...)`, начисляя XP.

**Что меняет студент:** выбирает метод с правильным названием и эффектом.

**Контрактный тест:** XP не меняется, задача отсутствует в обоих списках.

### B3. Подтверждение удаления

**Эталонное решение:** первое нажатие вызывает `confirmTaskDeletion`; кнопки «Да» и «Нет» используют callback с ID задачи.

**Стартовый patch:** первое нажатие сразу удаляет задачу вместо показа вопроса.

**Что меняет студент:** заменяет прямое удаление на готовый вызов `confirmTaskDeletion`. Кнопки «Да» и «Нет» уже формируются фасадом.

**Зависимость:** сначала должна быть решена B2, иначе кнопка «Да» всё ещё выполняет задачу вместо удаления. Поэтому B3 не входит в рекомендуемую пару первого урока.

**Контрактный тест после B2:** первое нажатие не удаляет; «Да» удаляет; «Нет» оставляет; XP неизменен.

### B4. Кнопка «Весь план»

**Эталонное решение:** кнопка `action:show_plan` вызывает `pet.showPlan(user)`.

**Стартовый patch:** удаляет кнопку и обработчик.

**Что меняет студент:** добавляет информационную кнопку и вызов готового метода.

**Контрактный тест:** порядок и отметки задач правильные до и после выполнения; XP не меняется.

## Единые источники учебных материалов

Не хранить копии постановок задач в репозитории. Единственный источник студенческих формулировок — двенадцать GitHub Issues репозитория. `prepare-lesson` выводит четыре прямые ссылки выбранного маршрута в рекомендуемом порядке.

Рекомендуемые независимые пары для 90 минут: Study — S1 + S3, Sport — I1 + I3, Blog — B1 + B4. Задачи S3/S4 идут после S1, I2 — после I1, B3 — после B2; эти зависимости должны быть явно указаны в GitHub Issues и методичке.

Ответы, теория, сетап и troubleshooting находятся в единой закрытой методичке МОПа в Notion. Так студент видит только постановку своей задачи, а МОП получает точное исправление, объяснение простыми словами, команду проверки и точку спасения в одном документе.

Репозиторий хранит только исполняемую учебную механику: три bundle-patch-файла, route-классы, тесты, скрипты подготовки и ссылочную навигацию в `README.md`.

## Обновить стартовые patch-файлы

Один patch маршрута содержит четыре изменения:

- два намеренных дефекта;
- удаление wiring двух функций;
- ровно четыре маркера `TODO STUDENT`;
- никаких изменений в Telegram-адаптере, SQLite-репозитории или AI-клиенте.

После применения patch проект обязан компилироваться. Базовый путь до места воспроизведения каждого бага должен оставаться доступным.

## Обновить prepare-lesson

Интерфейс можно оставить прежним:

```bash
./scripts/prepare-lesson.sh "Имя Фамилия" study|sport|blog
```

После подготовки скрипт выводит:

- путь к worktree;
- Pet и маршрут;
- четыре ссылки на GitHub Issues по порядку;
- рекомендуемые одну или две задачи для текущего урока;
- напоминание заполнить только `TELEGRAM_BOT_TOKEN`.

После применения и проверки bundle-patch скрипт сохраняет стартовый backlog отдельным commit. Поэтому начальный `git status` пуст, а `git diff` после работы показывает только изменения ученика.

Preflight должен проверять, что после patch появились ровно четыре `TODO STUDENT`, а не один.

## Тесты

Добавить по одному контрактному тесту на каждую задачу. Имена тестов должны совпадать с issue-кодами:

```text
studyWrongPet
studySavesCustomName
studyShowsPet
studyRenamesPet
sportLevelsAtOneHundred
sportShowsCurrentLevelImage
sportShowsHint
sportShowsLevelProgress
blogShowsActiveTasks
blogDeletesWithoutXp
blogConfirmsDeletion
blogShowsFullPlan
```

В чистом `main` все двенадцать тестов проходят.

`verify-lesson-patches.sh` для каждого маршрута:

1. копирует чистый проект;
2. применяет route-patch;
3. проверяет компиляцию;
4. подтверждает наличие четырёх `TODO STUDENT`;
5. подтверждает, что четыре соответствующих контрактных теста не проходят;
6. отменяет patch;
7. подтверждает, что эти же тесты проходят на эталонном решении.

Каждый GitHub Issue содержит отдельную команду запуска только своего теста, чтобы студент не видел ошибки трёх ещё не выполненных задач.

Не использовать в студенческом README слова `adapter`, `callback`, `state machine`, `facade`, `repository` и `fallback` без немедленного объяснения обычными словами.

## Рекомендуемый урок

Четыре Issues — backlog маршрута, а не обязательный объём одной встречи.

Для первого пилота:

- новичок без опыта: первый баг + первая функция;
- уверенный новичок: два бага + одна функция;
- человек с опытом: все четыре задачи или две функции после самостоятельной диагностики.

МОП останавливает техническую часть после второго полноценного результата, чтобы сохранить время на эволюцию Pet, рефлексию и презентацию курса.

## Критерии готовности walkthrough

- [ ] В `main` реализованы и проверены все двенадцать правильных решений.
- [ ] Учебная поверхность разделена на `StudyLesson`, `SportLesson` и `BlogLesson`.
- [ ] Каждый route-patch создаёт ровно два бага и две незавершённые функции.
- [ ] После patch проект компилируется и остаётся доступным для ручной проверки.
- [ ] Созданы двенадцать GitHub Issues и двенадцать ответов в единой методичке МОПа.
- [ ] Для каждой задачи существует отдельный контрактный тест.
- [ ] README приводит новичка к нужному файлу без знания архитектурных терминов.
- [ ] `prepare-lesson` выводит четыре ссылки выбранного маршрута и оставляет чистый `git status`.
- [ ] Новичок решает один баг и одну функцию за 35–40 минут практики.
- [ ] Изменения одного маршрута не ломают два остальных.
